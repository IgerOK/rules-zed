# Перенос конфигурации Zed-агента

Документ объединяет все правила в одном файле и рассчитан на **свежую установку Zed IDE на другом компьютере**: глобальный AGENTS.md (с блоками «Project Bootstrapping» и «Лимиты и экономия токенов»), skills `git-workflow` и `project-doctor`, рекомендация провайдера/модели (Agnes / `agnes-3.0-flash`, подробная настройка LLM — https://github.com/IgerOK/zed-free-llm).

Скопируйте этот файл на целевую машину. Текст написан так, чтобы его можно было передать агенту
целиком: откройте **новый** агент-чат в Zed и скажите: *«прочитай файл
`rules-Zed.md` и выполни инструкции §1–§6»* — папка с файлом при этом открыта в Zed
как проект (надёжнее, чем вставлять текст вручную; если так нельзя — вставьте
весь текст файла в чат). Агент делает всё по порядку: §1 → глобальный `AGENTS.md`
(путь по ОС, каталог создаст, если нет), §2 и §5 → `~/.agents/skills/<name>/SKILL.md` (каталоги
создаст, если нет), §3 — провайдер LLM в настройках Zed, затем сверяет себя по чек-листу §6 и
отчитывается, какие файлы созданы. Если файл/каталог создать нельзя (нет прав) — остановитесь и
назовите пользователю точный путь и что сделать вручную; если файл уже существует — не перетирайте
(добавьте только отсутствующие секции, покажите diff перед записью). Правила и skills вступают в силу
с **нового** агент-чата (список фиксируется при создании треда).

## 1. Глобальный AGENTS.md

Путь зависит от ОС (ОС определи сам — из окружения/терминала, или уточни у пользователя; каталог создай, если нет):
- Windows: `C:\Users\<USER>\AppData\Roaming\zed\AGENTS.md`
- Linux: `~/.config/zed/AGENTS.md`
- macOS: `~/Library/Application Support/zed/AGENTS.md`

Если файл **уже существует** — не перетирай: добавь только отсутствующие секции и покажи diff перед записью.

Если файла нет — создай с содержимым ниже (слово-в-слово).

```markdown
## Коммуникация
- Действуй как элитный Senior-разработчик: код должен быть лаконичным, безопасным, снабженным типами и строго структурированным.
- Отвечай без лишних приветствий, вводных слов и вежливых фраз — сразу к делу: коду или вызову инструментов.
- Всегда отвечай на русском языке, независимо от языка запроса или кода.
- Git-терминология в разговорной речи: «делаю коммит» / «создаю коммит»; глагол «коммить» в общение не использовать.

## Git
- При начале работы с проектом проверяй, установлен ли Git и инициализирован ли репозиторий — через глобальный skill `git-workflow` (установка, настройки пользователя, `.gitignore`, статус). По умолчанию — только локальный git.
- Пользователь может отказать (установка Git, создание репозитория) — тогда продолжай без Git и больше не предлагай это в данном проекте.
- После завершённого изменения в проекте (правка/создание/удаление файлов) — сразу создавай коммит, без отдельного запроса пользователя; формат — по правилу «Commit message» ниже.
- Работай по умолчанию только с локальным git: remote не настраивай и не делай пуш по своей инициативе. Пуш выполняй лишь по отдельной просьбе пользователя — по шагу 6 skill `git-workflow`.
- Commit message: subject — до 50 символов, с заглавной, в повелительном наклонении, без пунктуации в конце; body — перенос на 72 символа, только если полезен; возвращай только сообщение, без мета-комментариев.

## Python
- При начале работы с проектом проверяй, установлен ли Python (`python --version`; на Windows при неудаче — `py --version`).
- Если отсутствует — предложи установку: пользователь сам (Windows — инсталлятор с https://www.python.org с отметкой «Add Python to PATH»; Linux — `apt`/`dnf`/`pacman`; macOS — `brew install python`) или агент с согласия пользователя (`winget install Python.Python.3.14` или новее / системный менеджер пакетов / `brew`).
- Пользователь может отказать — тогда не предлагай повторно в данном проекте.

## Project Bootstrapping
- Если агент обнаруживает абсолютно пустую директорию проекта: 1) уточни у пользователя желаемый стек (например, Node.js/TypeScript, Python, Rust), 2) разверни базовую структуру (инициализация пакетного менеджера, `.gitignore`, базовый `README.md`), 3) настрой локальный `AGENTS.md` под выбранный стек.
- В любом проекте (включая существующие) должен быть проектный `AGENTS.md`: только проектно-специфичный контекст, без дублирования глобальных правил. Если отсутствует — попроси агента написать начальный по глобальным правилам, пользователь проверяет. Держи актуальным, как README: это экономия токенов и бесшовный переход в новый чат.

## README
- Если в проекте есть README.md — всегда приводи его в соответствие с текущим состоянию проекта.
- Если задача меняет структуру, возможности, команды сборки/запуска — обновляй README в рамках той же работы.
- Если README устарел относительно кода — укажи на это и исправь.

## Оболочка Windows (cmd / PowerShell)
- На Windows для выполнения команд агент выбирает оболочку под задачу —
  командную строку `cmd.exe` или `PowerShell`; единой обязательной нет:
  - `cmd.exe` — простые операции и Windows-специфика: `copy`/`move`,
    переменные `%VAR%`, редиректы, удаление файлов с зарезервированными
    именами (`nul`, `con`, `com1`) через `del` с префиксом `\\?\путь`.
  - `PowerShell` — файловая система и .NET: `Copy-Item`, `Get-ChildItem`,
    `[System.IO.File]::...`, переменные `$env:VAR`, конвейеры.
- Терминал Zed на Windows — POSIX-шелл (`sh`/Git Bash): он искажает
  Windows-пути (префикс `\\?\`, обратные слеши, `C:\...`). Для таких
  операций явно вызывай `cmd` или `powershell` из шелла.
- Бери ту оболочку, где операция короче и надёжнее; не привязывайся к одной.
- Файл с зарезервированным DOS-именем (`nul`, `con`, `com1`, `aux`, `prn`) стандартными командами не удалить — имя резолвится в устройство. Удалять через путь с префиксом `\\?\`: `del \\?\путь` в `cmd` или `[System.IO.File]::Delete("\\?\путь")` из .NET. Существование проверять через `Get-ChildItem` / `Directory.GetFiles` (`Test-Path` с `\\?\` не работает). Если прямой `cmd /c '...'` из POSIX-терминала Zed не выполняется (уходит в интерактив) — вынеси команду в файл `.cmd`/`.ps1` и запусти файл.
- Файлы конфигурации Zed: Windows — %APPDATA%\zed, Linux — ~/.config/zed, macOS — ~/Library/Application Support/zed (настройки, глобальный `AGENTS.md`, история чатов).

## Лимиты и экономия токенов
- Модель Agnes 3.0 Flash (документация: https://www.agnes-ai.com/en/docs/agnes-30-flash; на 10.2026 — бесплатный тариф, все виды запросов $0; контекст 512K / вывод 65.5K). Квоты 1 500 запросов / 5 ч, 15 000 / неделя, эффективный RPM 20: жёсткие лимиты в доках больше не публикуются (перенесены в entitlements аккаунта) — сверяй с документацией на сайте Agnes и дашбордом провайдера. Для другой модели/агрегатора — узнай лимиты или уточни у пользователя, заменив строку с моделью.

### Адаптивные профили
Числовые пороги — доли от окна W. Определи W из доков модели/шлюза и зафиксируй в проектном `AGENTS.md` (строка «Окружение: W = …K, профиль: …»); если W неизвестно или не зафиксировано — уточни у пользователя, не подставляй дефолт молча:
- **Узкое (W ≤ 128K):** чтения > 200 строк, вывод ≤ 30, handoff при 0.40·W.
- **Стандартное (129K < W ≤ 200K):** чтения > 500, вывод ≤ 50, handoff при 0.65·W.
- **Широкое (W > 200K):** чтения > 1000, вывод ≤ 100, handoff при 0.70·W.

### Пороговые триггеры
- **0.30·W** — точечный режим: grep/структура вместо чтения файла.
- **0.55·W** — запрет на новые подзадачи; довести текущую, чекпоинт-заметку в файл.
- **0.65·W** — handoff → новый чат.
Для узкого профиля: 0.25 / 0.40 / 0.45.

### Жёсткие лимиты
- Контекстное окно — верхняя граница, не цель. Комфортный объём: 0.75·W (стандарт/широкое), 0.50·W (узкое).
- Задача требует большого контекста (огромные файлы, массовые операции) — предупреждай до начала.
- При повторяющихся 429 / rate-limit — резервный API-ключ (провайдер) в Zed (Settings → Models).

### Точечное чтение
- Файлы > 500 строк (стандарт) / > 200 (узкое): grep/ripgrep по символу/функции, затем чтение диапазона.
- Не читать файл целиком, если решается фрагментом; не пересылай — только релевантные фрагменты.
- > 2000 строк / > 500 (узкое) — уточни: весь или фрагмент.
- Включи семантический индекс Zed (Settings → Indexing).
- Для больших монорепо — открывай в Zed поддиректорию задачи, не весь репо.

### Терминал
- Вывод: `| head -50` (стандарт) / `| head -30` (узкое) / `| head -100` (широкое); PowerShell — `Select-Object -First N`.
- Лог > 500 строк — окном 200–500, выводы → файл-заметку.

### Дробление длинных входов
- > 0.5·W (стандарт) / > 0.35·W (узкое) — разбей, обрабатывай последовательно.
- Промежуточные выводы → файл-заметку, не в историю чата.
- Не пересказывай обработанные части — ссылка на файл-заметку.

### Handoff-протокол
При достижении порога handoff:
1. Запиши в `HANDOFF.md` (корень или `.notes/`): цель (1–3 строк), сделано (файлы/строки), текущее состояние (открытые диффы), принятые решения (что и почему), следующие 2–3 шага, подводные камни.
2. Новый чат: «прочитай HANDOFF.md и продолжи».
3. HANDOFF.md удаляй после закрытия задачи.

### Чистый чат
- Новая крупная задача — новый агент-чат.
- Не держи в одном чате несколько несвязанных задач.
- Список skills/правил фиксируется при создании треда; изменения в AGENTS.md видны только в новом чате.

### Никаких лишних tool-схем
- MCP — только при реальной необходимости (свежие доки, E2E, БД). Каждый сервер — постоянная трата токенов в каждом запросе.
- Перед подключением: покрывает ли задачу нативный инструментарий Zed (файлы, терминал, grep, диагностика, fetch).
- Не подключать «на всякий случай».

### Проектный AGENTS.md
- Стек, версии, команды, конвенции, запретные зоны. Без секретов.
- **Записывай принятые решения и отклонённые варианты** («X сделали, Y отбросили, потому что Z») — экономия между сессиями.
- Не дублировать глобальные правила. Держать актуальным, как README.

### Сжатые ответы
- По делу, без повторов и пересказа кода из diff.
- Не выводить полные файлы, если изменилась одна функция — только diff.
- Не здороваться, не извиняться, не резюмировать очевидное.

### Параллельные вызовы
- Независимые tool-calls — параллельно (одним блоком).
- Перед серией: нет ли дублей к тем же файлам.
- Слияние диффов: накапливай, применяй одним tool call; файлы не перезаписывать целиком.

### Вложения и изображения
- Не вставляй картинки/скриншоты в чат — дорогие токены в каждом последующем запросе треда.
- Сохраняй в файл проекта, ссылайся по пути; агент прочитает точечно.

### Планирование по квоте
- В начале марафонской задачи: оцени N tool-calls, разложи по окнам (1 500 / 5ч, 15 000 / нед).
- > 75% дневного лимита — разбей на циклы с паузами.

### Оценка бюджета
- Перед крупной задачей (1 строка): «~N файлов, ~M tool-calls, влезет / разбить на K чатов».
- Если оценка бьётся о порог триггеров — разбей до начала, не на середине.

### Принцип одной попытки
- Синтаксическая ошибка → исправь ровно один раз. Повторилась → остановись, управление пользователю.
```

## 2. Глобальный skill: git-workflow

Каталог: `~/.agents/skills/git-workflow/` (создай, если нет). Файл `SKILL.md`:

````markdown
---
name: git-workflow
description: Проверка и настройка Git перед началом работы с кодом: установка Git (при отсутствии), инициализация репозитория, .gitignore, настройки пользователя, статус, коммит после изменений; remote и пуш — только по отдельной просьбе пользователя.
---

# Git Workflow — подготовка проекта

## Когда использовать
- При открытии нового проекта
- Перед началом работы с кодом
- Если нужно убедиться, что Git настроен правильно

## Git Path (Windows)
Полный путь к Git на Windows: `C:\Program Files\Git\cmd\git.exe`.
Оболочку выбирай под задачу (единой обязательной нет):
- PowerShell: `& "C:\Program Files\Git\cmd\git.exe" ...`
- cmd: `"C:\Program Files\Git\cmd\git.exe" ...`
Полный путь нужен, когда `git` нет в PATH терминала Zed; если `git` доступен — просто `git ...`.

## Проверки и действия

### 1. Проверить, установлен ли Git
`git --version`
Если команда не найдена — предложить пользователю установить Git (ОС определить самому или уточнить у пользователя), два варианта:
- Пользователь установит сам: Windows — инсталлятор с https://git-scm.com; Linux — `sudo apt install git` / `sudo dnf install git` / `sudo pacman -S git`; macOS — `brew install git`.
- Агент установит (только с явного согласия пользователя): Windows — `winget install Git.Git`; Linux — системный менеджер пакетов; macOS — `brew install git`.
После установки PATH может потребовать перезапуск терминала/сессии — затем вернуться к шагу 1.

### 2. Проверить инициализацию репозитория
`git -C <project_path> status`
Если ошибка `not a git repository` — выполнить `git init <project_path>`.

### 3. Проверить настройки пользователя (обязательны для коммитов и пушей)
`git config --global user.name` и `git config --global user.email`.
Если пустые — спросить у пользователя имя и email (подсказка: имя/email, совпадающие с аккаунтом на Git-хостинге, упрощают привязку коммитов и пушей), затем:
`git config --global user.name "User Name"` / `git config --global user.email "email@example.com"`.

### 4. Проверить .gitignore
Если отсутствует — создать минимальный шаблон под **стек проекта** (определяется по
манифестам). Пример для C/C++/Arduino:

```gitignore
# Компилятор Pelles C
*.obj
*.exe
*.lib
*.map
*.tds
*.rc

# Arduino IDE / PlatformIO
*.bin
*.elf
*.hex
.platformio/
build/
tmp*

# Windows
Thumbs.db
.DS_Store

# Zed
.zed/
```

Другие стеки: JavaScript/Node — `node_modules/`; Python — `__pycache__/`, `.venv/`;
Rust — `target/`. Для любого стека добавлять системный хлам (`Thumbs.db`, `.DS_Store`)
и каталог Zed `.zed/`.

### 5. Показать статус
`git -C <project_path> status` и `git log --oneline -5`.

### 6. Пуш (только по отдельной просьбе пользователя)
По умолчанию — локальный git: шаги 1–5 и 7 remote не настраивают. Если пользователь отдельно просит пуш:
`git -C <project_path> remote -v` — проверить, настроен ли remote.
Если нет или отсутствует доступ — запросить у пользователя адрес хранилища и один из способов аутентификации:
- HTTPS + персональный токен (PAT): `git remote add origin https://github.com/<user>/<repo>.git`.
- SSH-ключ: `git remote add origin git@github.com:<user>/<repo>.git`, проверить доступ `ssh -T git@github.com`.
Перед первым пушем спросить подтверждение.

### 7. Коммит после изменения
После каждого завершённого изменения в проекте (правка/создание/удаление файлов) — всегда создавать коммит, без отдельного запроса подтверждения; формат сообщения — по глобальному правилу «Commit message».
`git add .` → `git commit -m "..."`.

## Важно
- Устанавливать Git только с явного согласия пользователя (пользователем самим или агентом).
- Создавать коммит после каждого завершённого изменения в проекте (без отдельного запроса подтверждения).
- По умолчанию remote не настраивать и не пушить по своей инициативе — только по отдельной просьбе пользователя (шаг 6).
- Не создавать ветки без разрешения пользователя.
- Токены не записывать в файлы конфигурации и не включать в командную историю; при HTTPS аутентификацию выполняет менеджер учётных данных Git.
- Фиксировать, какие файлы были изменены (контекст изменений).
````

## 3. Провайдер и модель (настройка Zed)

Рекомендуется задействовать провайдера **Agnes** (модель `agnes-3.0-flash`).
Подробная настройка LLM в Zed (и бесплатные альтернативные агрегаторы) —
в отдельном репозитории https://github.com/IgerOK/zed-free-llm. Правила
AGENTS.md и skills к провайдеру не привязаны — существующие провайдеры
пользователя не заменяй.

### Почему Agnes 3.0 Flash

- **Специализация под агентные кодинг-задачи (Agnes Code)** — стабильное
  выполнение от понимания требования до финальной доставки: меньше зацикливаний,
  неэффективных tool-calls и ложных «готово».
- **Flash-класс (низкая латентность)** — важно, когда агент делает десятки
  tool-calls в задаче; здесь проигрывают тяжёлые «думающие» модели.
- **Контекст 512K** — влезает проект целиком, удержание целей и ограничений
  на многошаговых задачах (лимитами — блок «Лимиты и экономия токенов» AGENTS.md).
- **Thinking mode с настраиваемым budget** — точное управление ценой/качеством размышлений.
- **На текущий момент — бесплатный тариф** (квоты:
  https://www.agnes-ai.com/en/docs/agnes-30-flash#limits-and-pricing);
  модель остаётся дешёвой и после квот.

## 4. Нюансы skills и обновлений Zed

**Где живут skills** (проверено на Zed 1.18.x, Windows; актуальный стабил — 1.23.x, факты не перепроверены на новой версии — после обновления Zed проверь блок заново):
- Глобальные: `~/.agents/skills/<name>/SKILL.md` — доступны во всех проектах.
- Проектные: `<project>/.agents/skills/<name>/SKILL.md` — только в этом проекте.
- Если глобальный skill по какой-то причине не регистрируется — рабочая страховка:
  копия в проектном каталоге (создать в корне проекта).

**Требования к `SKILL.md`:**
- YAML frontmatter: `name` (строчные латинские, цифры, дефисы; совпадает с именем
  каталога) и `description` (кратко, 1–2 предложения).
- Кодировка UTF-8 **без BOM**, размер — несколько КБ (лимит на десятки КБ).
- Кириллица в `description` и тексте — допустима.

**Правило «нового чата» (главная причина «skill не виден»):**
- Список доступных skills фиксируется при **создании агент-треда**.
- Добавление skill-файла, перезапуск Zed, обновление версии — ни одно из этого
  не обновляет список в уже существующем треде (после рестарта Zed восстанавливает
  старые чаты с «замороженным» снимком).
- Чтобы новый skill (или изменённый AGENTS.md) применился — открыть **новый**
  агент-чат (New Thread) в нужном проекте.

**Обновление Zed (Windows):**
- Скачать Zed: https://zed.dev/?ref=taaft (Windows — инсталлятор
  `Zed-x.x.x-windows-installer.exe` или портативный `.zip`; macOS — `.dmg`; Linux — `tar.xz`).
- Ставить **поверх**: запустить новый инсталлятор (или распаковать портативку в
  `C:\Users\<USER>\AppData\Local\Programs\Zed`) — настройки и данные сохраняются.
- **Не удалять** `AppData\Roaming\Zed` и `AppData\Local\Zed` — там настройки,
  глобальный `AGENTS.md`, темы, история чатов. Skills живут отдельно в
  `~/.agents/skills` — их удаление Zed не затронет в любом случае.
- Полная чистка `AppData` — только при порче данных.
- Версию проверить: `Ctrl+Shift+P` → `Zed: About`.

**Чек-лист, если skill не виден агенту:**
1. Файл на месте, имя каталога = `name` в frontmatter, без BOM.
2. Открыт **новый** агент-чат (в старых тредах список заморожен).
3. Всё равно не видно → создать проектную копию `<project>/.agents/skills/<name>/SKILL.md`.

**Проектный `AGENTS.md` (важно для любого проекта — нового и существующего):**
- Файл `<project>/AGENTS.md` в корне кодинг-проекта — разовое создание; Zed
  подхватит его автоматически в новых агент-чатах, без какой-либо регистрации.
  Назначение — хранение контекста проекта: экономия токенов и бесшовный переход
  в новый чат.
- Содержимое — только **отличие** от глобального `AGENTS.md`: стек и версии
  (язык, фреймворки, версии тулов); точные команды сборки/запуска/тестов/линтинга
  (с флагами); конвенции (именование, структура каталогов, запретные зоны — что
  трогать нельзя); окружение (порты, имена переменных окружения **без значений**,
  БД, CI); требования к формату ответов/отчётов. Глобальные правила (commit
  message, git check, лимиты моделей) **не дублировать** — источник правды один.
- Секреты (ключи, токены, пароли) в файл не записывать — только имена переменных
  окружения или ссылки на файлы конфигурации.
- Держать файл актуальным по мере эволюции проекта — как README.
- Быстрый способ начать: попросить агента «изучи проект и напиши начальный
  `AGENTS.md` по правилам из глобального» — пользователь затем проверяет и
  дополняет.

## 5. Глобальный skill: project-doctor

Второй глобальный skill в дополнение к `git-workflow`: сразу после установки Zed
критично важно иметь сквозную диагностику здоровья среды разработки (манифесты,
зависимости, переменные окружения, линтеры) при открытии любого репозитория.

Каталог: `~/.agents/skills/project-doctor/` (создай, если нет). Файл `SKILL.md`:

```markdown
---
name: project-doctor
description: Сквозная автоматическая проверка готовности окружения проекта, целостности зависимостей, линтеров и конфигурационных файлов.
---

# Project Doctor — Проверка среды

## Когда использовать
- Сразу после открытия нового или только что клонированного проекта в Zed.
- Если проект перестал собираться или выдаёт неявные ошибки окружения.

## Алгоритм действий
1. **Диагностика структуры:** Проверить корень проекта на наличие файлов
   манифестов (`package.json`, `Cargo.toml`, `pyproject.toml`, `go.mod`).
2. **Анализ зависимостей:** Убедиться, что установлены локальные пакеты
   (папки `node_modules`, файлы блокировок `Cargo.lock` / `poetry.lock`,
   виртуальные окружения `.venv` / `venv`). Если отсутствуют — предложить
   запустить команду установки через встроенный терминал Zed
   (`npm install`, `cargo check` и т. д.).
3. **Проверка переменных окружения:** Проверить наличие образцов
   конфигурации (например, `.env.example`). Если локальный файл `.env`
   отсутствует, автоматически создать его копию и уведомить пользователя
   о необходимости заполнения секретных ключей.
4. **Инспекция линтеров и форматирования:** Найти файлы конфигурации
   кодовой базы (`.prettierrc`, `eslint.config.js`, `rustfmt.toml`). Если
   линтеры присутствуют, использовать их правила для проверки генерируемого
   кода.
```

## 6. Проверка

1. Прочитай созданные файлы и подтверди, что все 7 секций AGENTS.md (Коммуникация, Git, Python, Project Bootstrapping, README, Оболочка Windows (cmd / PowerShell), Лимиты и экономия токенов) и skills `git-workflow` и `project-doctor` на месте.
2. Подтверди, что в Zed настроен используемый провайдер и модель (настройка — по инструкции в https://github.com/IgerOK/zed-free-llm; рекомендуемое значение — Agnes / `agnes-3.0-flash`, допустим любой другой LLM-агрегатор).
3. Открой **новый** агент-чат и спроси у агента, какие skills доступны:
   в списке должны быть `git-workflow` и `project-doctor` (в уже открытом чате
   список заморожен — проверять в нём неинформативно).
4. Напомни пользователю: правила вступают в силу с **новой** агент-сессии (New Chat).
5. Выведи итог: какие файлы где созданы/изменены.
